# 센터 완료 통보 — 재시도와 실패 알림 (2026-11-26, 초안)

> 상태: **초안**. 아직 올리지 않았다(함수 배포·DB 적용 모두 대표 확인 뒤).
> 대표 결정(2026-11-26): 완료 통보가 끝내 실패하면 **더큰웍스 알림**으로 대표·담당 차장·개발 담당 대리 세 명에게 알린다.

## 1. 왜

학생이 훈련을 끝내면 `wordsense-complete` 가 게이트(service-back)의 완료 API 를 불러 센터에 「이 회차 끝남」을 알린다.
지금까지는 토큰 401 때 한 번 다시 부르는 것 말고는 재시도도 알림도 없어서, 게이트가 잠깐 답하지 않으면
**학생은 끝냈는데 센터에는 끝나지 않은 회차**로 남고 아무도 모른다.

## 2. 바뀌는 동작

| 게이트 응답 | 처리 |
|---|---|
| 200 | 성공(전과 같음) |
| 200 인데 `training_end_success:false` | 회차는 저장됨. **재시도하지 않는다** → 기록 + 알림(센터에서 손으로 처리) |
| 400 「이미 처리된 훈련 회차입니다.」 | **성공으로 취급**(입장권 완료 표시, 재시도·알림 없음). 화면에 가는 응답은 전처럼 400 그대로 |
| 401 | 토큰을 새로 받아 바로 한 번 더(전과 같음). 또 401 이면 실패 → 기록 + 알림 |
| 통신 오류 · 시간 초과 · 408 · 425 · 429 · 5xx | **재시도** |
| 400 「토큰 불일치」 | 1.5초 뒤 **한 번만** 더 부른다. 「이미 처리된」으로 바뀌면 성공(같은 입장권의 요청이 겹쳐 늦은 쪽이 된 경우), 그대로면 실패 → 기록 + 알림 |
| 그 밖의 4xx(결제 정보 없음 · 훈련 정보 없음 · 입력값 오류) | 다시 보내도 같은 답 → 재시도하지 않고 바로 기록 + 알림 |

**입장권 없는 구버전 호출**(sessionId 없이 payment_fn 만 보내는 길)은 전과 똑같이 한 번만 부르고 로그만 남긴다 — 재시도·실패 기록·알림 모두 없다.
로그인 없이 누구나 부를 수 있는 길이어서, 알림이나 기록을 일으키게 두면 알림 폭주·표 채우기에 쓰일 수 있기 때문이다.

### 재시도 횟수·간격

- 처음 1번 + 재시도 3번 = **모두 4번**. 재시도 전 기다림: **3초 → 12초 → 30초**.
- 한 번 부를 때 시간 제한: **첫 시도 25초**(게이트는 회차를 저장한 뒤 구 센터의 답을 기다렸다가 응답한다 — 너무 짧게 끊으면 저장은 됐는데 답만 못 받는 일이 생긴다), **재시도 15초**.
- **첫 시도만 응답 전에** 한다. 실패하면 화면에는 바로 답하고(전과 같은 오류 꼴 + `retrying:true`), 남은 재시도는 `EdgeRuntime.waitUntil` 로 **뒤에서** 돈다.
  화면은 `keepalive` 로 한 번만 부르므로 창을 닫아도 서버 쪽 재시도는 계속된다(Supabase 문서 「Background Tasks」: 응답을 먼저 보내고 `waitUntil` 에 넘긴 일은 작업자가 살아 있는 동안 계속 돈다).
- 뒤에서 도는 재시도는 가장 오래 걸려도 90초(한도 100초를 넘기게 되면 남은 재시도를 그만둔다).
- **시간 제한은 「요청 하나」가 아니라 「작업자(worker) 하나의 수명」** 이다(무료 150초·유료 400초, 여러 요청이 같은 작업자를 나눠 쓴다). 그래서 이미 오래 돈 작업자에서 시작한 재시도는 도중에 끊길 수 있다. 이를 전제로 두 가지를 해 두었다:
  1. **첫 실패 때 바로**(재시도를 시작하기 전에) 실패 기록을 남긴다 → 끊겨도 기록은 남는다.
  2. **훑기**: 함수가 요청을 받을 때마다(성공한 요청 포함) 뒤에서, 풀리지 않았고 알림도 못 간 채 5분이 넘은 줄을 3건까지 찾아 알린다 → 끊겨서 알림이 못 간 것도 다음 학생 요청 때 알림이 간다.
- 값은 `supabase/functions/wordsense-complete/retry.mjs` 맨 위(`FIRST_TIMEOUT_MS`, `RETRY_TIMEOUT_MS`, `RETRY_WAITS_MS`, `TOTAL_BUDGET_MS`, `TOKEN_RECHECK_MS`).

#### 훑기를 예약 작업(pg_cron)이 아니라 함수 안에 둔 이유

- 이 프로젝트 DB 에는 `pg_cron`·`pg_net` 이 **둘 다 꺼져 있다**(2026-11-26 확인). 예약으로 하려면 확장 둘을 켜고, DB 안에 함수 주소와 관리용 열쇠를 넣어 두어야 한다 — 설정할 것과 비밀을 둘 곳이 늘어난다.
- 함수 안 훑기는 **더 올릴 것도, 더 둘 비밀도 없다**. 조회 한 번(부분 색인)이고 응답 뒤에 돌아서 성공 경로를 늦추지 않는다.
- 약점: 요청이 하나도 없으면 돌지 않는다. 다만 학생이 결과 화면에 닿을 때마다 이 함수가 불리므로, 훈련이 이어지는 시간대에는 몇 분 안에 알림이 간다. 아무도 훈련하지 않는 밤에 끊긴 건은 다음 날 첫 요청 때 알림이 간다. 이것이 부족하면 그때 확장을 켜고 5분마다 `resend_failed` 를 부르는 예약을 더한다.

### 판단 근거 (게이트 소스 `service-back` dev 브랜치를 읽고 확인)

- **5xx 는 다시 보내도 안전하다**: 회차 저장은 한 트랜잭션 안에서 하고, 그 안에서 오류가 나면 저장이 취소된다(토큰도 그대로 남는다). 저장이 이미 된 경우에도 다시 보내면 「이미 처리된」이 올 뿐이다.
- **`training_end_success:false` 는 재시도 대상이 아니다**: 회차 저장이 커밋된 뒤 구 센터의 무료·추가 회차 처리(training_end)만 실패한 경우다. 이때 1회용 토큰(study_token)은 이미 소진됐고, 다시 보내면 「이미 처리된」 400 만 돌아와 무료·추가 회차 처리는 다시 돌지 않는다. 게이트도 「수동 확인 필요」로 로그를 남긴다 → 재시도 대신 **사람에게 알린다**.
- **답을 못 받은 시도 뒤 「이미 처리된」**: 통신 오류·시간 초과·502·503·504(게이트 앞단이 대신 답했을 수 있다) 뒤에 「이미 처리된」이 오면, 앞선 시도가 실제로는 저장된 것이다. 성공으로 취급하되 그때의 무료·추가 회차 처리 결과는 알 수 없으므로 `training_end_unknown` 으로 기록하고 **보통 등급 알림**을 보낸다. 토큰 발급 실패처럼 완료 API 를 부르지도 못한 시도는 여기에 넣지 않는다.
- **「토큰 불일치」를 한 번 더 부르는 이유**: 같은 입장권의 요청 둘이 겹치면, 먼저 온 쪽이 토큰을 쓰고 아직 커밋하기 전에 늦은 쪽이 「토큰 불일치」를 받는다. 잠깐 뒤 다시 부르면 「이미 처리된」으로 바뀐다. 이때 먼저 끝난 쪽이 `attempts` 에 남긴 200 기록은 덮어쓰지 않는다.

### 바뀌지 않는 것

- 성공 경로, 재훈련(`retry`)·결과 화면 단계(`deferred`)·복습(`review`)·이미 완료(`already_completed`) 처리, 응답 꼴. 응답에 `retrying:true` 한 칸이 더해질 뿐이다(재시도가 뒤에서 도는 중일 때만).
- 화면(`word-sense.html`)은 고치지 않는다.

## 3. 실패 기록 — `complete_failures` 표

`db/migrations/2026-11-26_complete_retry.sql`. 개인정보 없이 회원 번호·학원 번호·회차·게이트 응답만 남긴다. Edge Function 만 읽고 쓴다(RLS 잠금).

| kind | 뜻 | 다음 일 |
|---|---|---|
| `complete_failed` | 센터에 완료가 남지 않음 | **다시 보내기** 대상 |
| `training_end_failed` | 회차는 저장됐으나 무료·추가 회차 처리 실패 | 센터에서 손으로 처리 뒤 「풀림」 표시 |
| `training_end_unknown` | 무료·추가 회차 처리 결과를 모름 | 센터에서 확인 뒤 「풀림」 표시 |

첫 시도가 실패하면 그 자리에서(재시도를 시작하기 전에) 줄을 남기고, 뒤에서 도는 재시도가 성공하면 「풀림」으로 바꾼다(재시도 도중 작업자가 꺼져도 기록은 남는다).
입장권(session_init)이 있는 호출만 기록한다.
`attempts` 의 `service_back_status`·`service_back_message`·`training_end_success` 칸에는 전처럼 마지막 결과가 들어간다.

## 4. 알림

끝내 실패하면 더큰웍스 운영 알림 창구(`ops-alert`)를 부른다 → 알림함 + 푸시. 받는 사람은 더큰웍스 설정에서 정한다(이 저장소에는 이름이 없다).

- 보내는 내용: 회원 번호 · 학원 번호 · 회차 · 시각 · 시도 횟수 · 게이트 상태. **학생 이름·연락처는 보내지 않는다.**
- 묶음(폭주 방지): 게이트가 답하지 않는 경우·인증 실패는 종류마다 한 묶음 — 여러 학생이 한꺼번에 실패해도 창구가 정한 시간(기본 30분)에 알림 한 번. 묶여서 빠진 회차도 표에는 모두 남는다(알림 본문에 「풀리지 않은 실패 기록 N건」).
  건마다 사람이 처리해야 하는 것 — 이 회차만 거절된 경우, 무료·추가 회차 처리 실패(`training_end_failed`), 결과 모름(`training_end_unknown`, 보통 등급) — 은 회차마다 따로 알린다.
- 창구가 분당 상한(429)으로 답하면 알려 준 시간(길어도 60초) 뒤 **한 번** 다시 보낸다. 그래도 못 보낸 줄은 `alerted_at` 이 빈 채로 남아 훑기가 나중에 알린다.
- 환경변수(주소·비밀)가 없거나 알림 호출이 실패해도 **훈련 저장·학생 응답에는 영향이 없다**(기록만 남는다). 알림 호출은 응답 뒤에 한다.
- 계약: Biz-manager 저장소 `docs/운영알림_창구.md`.

## 5. 실패분 다시 보내기

같은 함수의 관리용 요청이다. 열쇠(`COMPLETE_ADMIN_KEY`, **32자 이상** — 더 짧으면 설정되지 않은 것으로 보고 닫는다)가 설정돼 있고 헤더가 맞을 때만 돈다.

```bash
# 무엇이 남아 있는지만 보기
curl -sS -X POST "https://<프로젝트>.supabase.co/functions/v1/wordsense-complete" \
  -H "Content-Type: application/json" -H "x-admin-key: <COMPLETE_ADMIN_KEY>" \
  -d '{"action":"resend_failed","dry_run":true}'

# 다시 보내기 (한 번에 최대 50건, 기본 20건)
curl -sS -X POST "https://<프로젝트>.supabase.co/functions/v1/wordsense-complete" \
  -H "Content-Type: application/json" -H "x-admin-key: <COMPLETE_ADMIN_KEY>" \
  -d '{"action":"resend_failed","limit":20}'
```

- `complete_failed` 가운데 풀리지 않은 줄을 오래된 것부터 한 건에 한 번씩 보낸다. 성공·「이미 처리된」이면 입장권 완료 표시 + 「풀림」.
- 게이트가 여전히 답하지 않으면 거기서 멈춘다(`stopped:"gate_unreachable"`). 나중에 다시 실행한다.
- 응답: `{ success, picked, resolved, still_failed, stopped, results:[{id, result, status}] }`
- 학생이 그사이 같은 회차를 다시 열어 끝냈으면 `already_completed` 로 풀린다. 학생이 달력에서 회차를 다시 시작해 새 토큰이 발급됐다면 옛 토큰으로는 「토큰 불일치」가 온다 — 이 경우는 학생이 새 입장권으로 끝내면 해결된다.

SQL 로 보기·손으로 풀림 표시(Supabase SQL Editor):

```sql
-- 풀리지 않은 실패
SELECT id, kind, member_no, academy_no, training_round, last_status, last_message, tries, first_failed_at, alerted_at
FROM complete_failures WHERE resolved_at IS NULL ORDER BY id;

-- 센터에서 손으로 처리한 뒤 풀림 표시
UPDATE complete_failures SET resolved_at = now(), resolved_how = 'manual' WHERE id = <번호>;
```

## 6. 환경변수 (Supabase › Edge Functions › Secrets, 값은 문서에 쓰지 않는다)

| 이름 | 뜻 | 없으면 |
|---|---|---|
| `OPS_ALERT_URL` | 더큰웍스 운영 알림 창구 주소(`…/functions/v1/ops-alert`) | 알림 없이 기록만 |
| `OPS_ALERT_SECRET` | 그 창구의 한자어포스용 공유 비밀(더큰웍스의 `OPS_ALERT_SECRET_WORDSENSE` 와 같은 값) | 알림 없이 기록만 |
| `COMPLETE_ADMIN_KEY` | 「실패분 다시 보내기」 열쇠(32자 이상의 무작위 문자열) | 다시 보내기 닫힘(503). 32자 미만도 같다 |

## 7. 올리는 순서 (테스트 프로젝트 → 확인 → 운영)

1. 더큰웍스 쪽 창구를 먼저 올린다(`docs/운영알림_창구.md` 의 순서).
2. 이 프로젝트 DB 에 `db/migrations/2026-11-26_complete_retry.sql` 실행.
3. Secrets 에 위 세 값을 넣는다.
4. 함수 배포 — **파일 두 개를 반드시 함께 올린다**: `index.ts` + `retry.mjs`(`retry.test.mjs` 는 올리지 않아도 된다).
   `supabase functions deploy wordsense-complete --no-verify-jwt`
   - ⚠ `retry.mjs` 가 빠지면 함수가 **부팅에 실패해 완료 통보 전체가 멈춘다**(학생이 끝내도 센터에 하나도 안 남는다). 도구로 파일을 골라 올릴 때 특히 주의한다.
   - 그래서 **테스트 프로젝트에 먼저 올려 정상 완료 한 번**(응답 200, `attempts`·`session_init.completed_at` 기록)을 확인한 뒤에 운영에 올린다. 운영에 올린 직후에도 정상 완료 한 번을 확인한다.
5. 아래 8번 시험.

순서가 어긋나도 훈련 저장은 안전하다: 표가 없으면 기록·다시 보내기만 빠지고, 알림 환경변수가 없으면 알림만 빠진다.

## 8. 시험

- 단위 시험(게이트·알림을 부르지 않는다): `node --test supabase/functions/wordsense-complete/retry.test.mjs` — 판정, 재시도 횟수·간격, 시간 한도, 「이미 처리된」, 401, 알림 본문·중복 방지 키.
- 테스트 프로젝트에서(게이트 개발 서버 8193):
  1. 정상 완료 한 번 → 응답·`attempts`·`session_init.completed_at` 이 전과 같은지.
  2. 같은 입장권으로 다시 finalize → `skipped:'already_completed'`.
  3. `SERVICE_BACK_BASE_URL` 을 잠깐 없는 주소로 바꾸고 finalize → 바로 502 + `retrying:true`, 그 자리에서 `complete_failures` 에 줄이 생기고, 약 1분 뒤 `tries=4`·더큰웍스 알림 한 번. 같은 일을 한 번 더 → 알림은 다시 오지 않고(묶임) 기록만.
  3-1. 입장권 없이(sessionId 없이 payment_fn·training_round 만) 같은 상태에서 호출 → 502 만 오고 `complete_failures` 에 줄이 **생기지 않고** 알림도 없는지.
  3-2. 훑기: 풀리지 않은 줄 하나의 `alerted_at` 을 비우고 `last_tried_at` 을 10분 전으로 바꾼 뒤(테스트 프로젝트에서만) 아무 요청이나 한 번 → 알림이 가고 `alerted_at` 이 채워지는지.
  4. 주소를 되돌리고 `resend_failed` → `resolved` 로 풀리고 센터에 완료가 남는지.
  5. 재훈련·결과 화면 단계(`defer_academy`)·복습 입장권 응답이 전과 같은지.
- 게이트 쪽 5xx·시간 초과를 일부러 내는 시험은 성효민 대리와 맞춰서 한다.

## 10. 알고 있는 한계

- 재시도는 약 1~2분 안에서만 한다. 게이트가 그보다 오래 멈추면 실패로 남고 알림이 가며, **다시 보내기는 사람이 실행**한다(자동으로 다시 보내는 예약은 만들지 않았다 — 2번의 「훑기」는 알림만 보낸다).
- 뒤에서 도는 재시도 도중 작업자가 수명이 다해 꺼지면 그 자리에서는 알림이 안 간다. 기록은 첫 실패 때 이미 남아 있고(`alerted_at` 이 비어 있음), 5분 뒤부터 다음 요청의 훑기가 알린다. 요청이 전혀 없는 시간에는 그만큼 늦어진다.
- 같은 입장권으로 요청이 겹치면 게이트를 두 번 부를 수 있다. 게이트는 한 번만 저장하고, 늦은 쪽에는 「이미 처리된」 또는(먼저 온 쪽이 커밋하기 전이면) 「토큰 불일치」로 답한다 — 뒤의 경우는 1.5초 뒤 한 번 더 불러 「이미 처리된」을 확인하고 성공으로 본다. 그때도 「토큰 불일치」면 실패로 기록하고 알린다.
- 입장권 없는 구버전 호출은 재시도·기록·알림이 없다(2번 참고). 지금 화면은 항상 입장권을 보낸다.
